# tutorial-main-3.1 性能专项

2026-10-04–05；用户指定真实教程文档并已授权运行和测试。此项独立于首版发布依赖。

## 方法与复用

复用现有 `group_drag_benchmark.gd` 的真实指针拖动、隔离的 Stage 和文档副本加载；使用 Godot 原生 `Time`、`RenderingServer`、`Performance`、`FileAccess`，不增加依赖。测试探针继承项目脚本，只对实际回调计时，不手动重放回调，也不修改生产脚本或用户偏好配置。

`tests/performance_baseline.gd` 是编辑器运行时入口，`performance_baseline_runner.gd` 是可用于 Release 场景的同一个测量逻辑。每阶段测量 3 秒，输出帧时间 median/P95/P99、渲染 CPU/GPU、回调 CPU、静态内存、显存和 Linux RSS。原文档复制到用户目录，结束后删除副本并校验哈希；不保存原文档。

原生视口 CPU 指标只含渲染操作，不包含脚本和其他子系统；GPU 完整统计应覆盖每帧绘制的所有视口。本基准同时保留舞台视口和已枚举视口总和。参见 [Godot RenderingServer 文档](https://docs.godotengine.org/en/latest/classes/class_renderingserver.html#class-renderingserver-method-viewport-get-measured-render-time-gpu)。子视口可能按需更新，不能把未更新视口残留时间的总和视为精确的整帧关键路径。

回调计时是 inclusive 时间：`overview.refresh` 包含在 `overview._process` 内，`layer.refresh_layout` 包含在 `layer._process` 内；不可重复相加。物理回调按显示帧归一化，包含补帧时的多次物理调用。加载阶段按相邻帧采样标签归属，包含调度和渲染等待，不是各函数纯 CPU 时间。

回调使用单调时钟记录经过时间，含线程被操作系统抢占的等待；它是函数开销的定位证据，不是线程 CPU 计费数据。测量运行在共享桌面，保留 Linux load average，存在调度和频率变化；不把跨次波动描述为优化收益。

## 三次 Release 基线与诊断

独立导出的 Linux Release，`debug_build=false`，使用正式 4.8-dev6 Release 模板；生产项目文件和保存的导出预设未修改。构建时仅临时替换内存中的 main scene，随后恢复为 `res://src/boot/boot.tscn`，磁盘配置与内存配置均已核对。基准不经过生产单实例启动重定向。

三次都使用同一个 PCK：SHA-256 `6599b18ca5aae9a9466f30da55ae835067fb2f5c812cc382e1819edd485bb2a4`，源 HEAD `cbae8471c3a728064f838e1c6b33201fbe409e62` 加已有工作区改动。七次 Release 的完整汇总数据保存在 [performance-baseline-results.json](performance-baseline-results.json)；`final1/2/3` 为正常基线，其余为指定诊断开关。

下面各列是三次运行对应统计量的中位数，不是合并所有帧后重新计算的分位数。

拖动平均每显示帧的回调开销：概览 5.04–5.73 ms（其中 native preview 更新检查 0.71–0.82 ms）；层级物理传播 2.46–3.26 ms；层级 render process 2.03–2.50 ms（其中 layout 0.83–1.02 ms）；舞台 process 1.22–1.55 ms。连线概览更新仅 0.004–0.006 ms，不代表所有真实连线的物理/几何开销。

拖动中根窗口与舞台视口 GPU 时间之和的中位数为 0.47–0.51 ms，渲染 CPU 中位数在原始数据中保留。每个阶段开始枚举现有视口；动态一次性缩略图另行记录完成捕获次数。三次拖动均未观测到新的缩略图捕获完成。一次性视口计时读数均为 0，因此记作**未取得有效 GPU 计时**，不记作零成本；尚不能宣称完整 GPU profiling 已覆盖所有瞬时视口。

Release 的 `MEMORY_STATIC` 返回 0，不可用。通过按行读取 `/proc/self/status` 采集实际 RSS，拖动阶段为 622–626 MiB；显存保留在原始数据中。静态内存、RSS、显存互有不同统计口径，不能直接相加。

| 暂停概览回调 | 28.913 / 53.853 / 60.673 | 有降低典型帧开销的信号，但尾帧仍重；不能删除概览功能作为交付 |

## 固定条件与 Debug 交叉检查

文档：`tutorial-main-3.1.prg`，974 个对象，SHA-256 `8c6b139e45ce677131b58c360e401b677ce6dbfefd4c05db3a5574f8f9d8b553`。

环境：Godot 4.8-dev6 official `8898c2b3db32adf6f92c694ffb6dac19af672e5f`；i9-13900H / Iris Xe RPL-P；Mobile/Vulkan；窗口 1996×1248，实际舞台视口 1152×648，透明窗口开启，VSync 关闭。测量围绕“伸缩链”分组，基础 zoom 0.284882，缩放轨迹为基础倍率 ±25%。裸 Stage 不包含主界面的菜单、调试面板或标签页。

最终基准另做一次 Debug 交叉检查，通过对象数、引用、移动及文件校验：打开 4138 ms；整图缩放帧时间 5.475 / 8.185 / 11.461 ms，拖动 47.401 / 59.184 / 80.798 ms；拖动 RSS 674 MiB。该单次结果仅用于检查基准运行，不能与 Release 的统计差异当作代码优化收益。共享工作区已有大量未提交功能，基线针对当前工作区而非单独 HEAD。

尚未细分的剩余帧时间包括真实连线、碰撞形状、原生物理及调度，不能归因于 GPU。一次进程内的内存增长也不能证明泄漏。

## 着色器和其他方案的判断

当前证据支持先优化项目更新范围：拖动帧时间远高于静止，实际概览和层级回调开销可见，已有视口的渲染计时较低。局部 shader 保留为已测 CPU 几何热点的候选，尚不支持优先重写全部着色器或自行编译、修改 Godot 渲染器。需要瞬时子视口和完整主界面 profiling 后再形成最终平台结论。

| 方案 | 对应问题 | 优先级与约束 |
| --- | --- | --- |
| 只刷新脏对象、脏分组 | 不相关对象反复更新、全局缓存失效 | 首选；复用现有 geometry revision 和成员缓存，保留编辑/撤销语义 |
| 平移复用几何、缓存局部轮廓 | 拖动时重复建立碰撞和边框 | 首选候选；尺寸、文字、成员变化仍须正确失效；用相同拖动轨迹比较 |
| 连线局部更新、缓存曲线 | 端点变化引发重复重算 | 先补实际计时；连接、命中和箭头必须同步 |
| 批量、分帧加载和预览准备 | 打开时创建/几何/概览阶段卡顿 | 保留现有渐进加载架构，优先缩短最长的初始概览阶段 |
| 视口裁剪和缩放细节等级 | 不可见或过小内容仍处理，概览反复生成 | 复用现有概览与文字细节机制；检查首次缩放、边界来回和点击命中 |
| 局部 CanvasItem shader | 已证实的边框/连线 CPU 几何更新 | 有条件候选；若只替换像素着色，不会自动消除物理、排版和缓存更新。必须给出 CPU 几何重建减少的实测证据 |
| C# / GDExtension | 项目层收敛后仍重的计算热点 | 后续候选；先评估已有 Godot 原生几何能力，再决定是否迁移；引入编译和跨平台维护成本 |
| 修改引擎渲染器 | 引擎内部渲染成为主要瓶颈 | 当前不支持；需 Release 中原生渲染占主导且上述项目方案仍不足的证据 |

本轮没有新增 shader，也没有把尚未完成的热点优化描述为已实现。

## 复测与手动验收

通过 Godot MCP 启动 `tests/performance_baseline.gd`，传入 `--fixture-hex=`（文档路径的 UTF-8 十六进制）。可用 `--opaque` 比较不透明窗口；`--disable-overview`、`--disable-shape-refresh`、`--disable-contact` 仅用于诊断，不能作为正常功能性能结果。`--ablation` 的禁用回调/隐藏画布阶段发生在拖动结束后，只反映静态开销，不能与拖动阶段作因果对照。

Release 复测：在 Godot MCP 编辑器脚本调用 `load("res://tests/performance_release_export.gd").build("/tmp/pg-performance-release.x86_64")`，返回 `OK` 后通过 MCP 执行导出的程序，并把相同 `--fixture-hex=` 放在 `--` 后。若文件没有可执行权限，通过 MCP 设置权限。构建生成 `tests/performance_release_entry.res`，无需手写场景文件；不要把测量用的临时导出包发布成产品版本。正式导出预设仍排除 tests。

手动打开同一文档：应显示加载预览并完整结束；在“伸缩链”区域拖动整个分组，再连续缩放及首次缩放，检查成员、边框、连线、箭头、文字清晰度、点击命中及透明背景。撤销/重做拖动应恢复整个操作，原文件内容应保持原样。失败时记录发生在加载、拖动或缩放的哪一阶段，重点检查缓存失效、几何同步、碰撞重建、预览释放和历史事务。

使用的 MCP 类别：脚本创建/修改、编辑器脚本执行、原生场景资源打包和临时导出。没有直接读写 `.tscn`，没有操作 Godot Editor UI，也没有修改第三方插件。

尚待完成：首次解码/排版/真实连线/碰撞函数的独立计时、瞬时预览 GPU profiling、更大真实文档、完整主界面、多平台及上述用户手动视觉验收。Debug 运行仍有已有的加载卡片 anchor 警告，Debug 和 Release 退出时均有 1 个 ObjectDB 泄漏警告，不能声称资源释放验收完成。
